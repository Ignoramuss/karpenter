# Reproducing the results

Every table and figure under `paper/`, and every verdict, effect and run count in `experiments/RESULTS.md`, is
regenerated by one command (`make figures`) from the raw runs in `experiments/runs/`, with VM epochs taken from
`experiments/session-driver/machine-log.txt`. Every raw run is regenerated from a commit, a configuration and a
seed. The decision-level parity counts come from `experiments/parity/` (Parity, below). The session's timeline, cut
projections and VM replacement times come from the session driver's records (`experiments/session-driver/`).

## Hardware and software of the session

- Claude Code cloud VMs: 4 vCPUs (one thread per core), 15 GiB RAM, Linux 6.18. The VM was replaced three times,
  so the runs come from four VMs in turn, epochs A-D in `experiments/session-driver/machine-log.txt`:

  | Epoch | Booted (UTC) | CPU as `lscpu` names it | Ran |
  | --- | --- | --- | --- |
  | A | before Oct 27 20:52 | Intel Xeon @ 2.10 GHz | session runs from 20:52 |
  | B | Oct 27, about 23:52 | Intel Xeon @ 2.80 GHz | session runs |
  | C | Oct 28 03:29:38 | Intel Xeon @ 2.10 GHz | session runs |
  | D | Oct 28 23:23:55 | Intel Xeon @ 2.80 GHz | the rest of the session, the H7 timing pass, the late parity chunks |

  A run's VM is the last boot at or before its manifest's `started_at`; the analysis derives it as the
  `machine_epoch` column. The clock labels are `lscpu`'s generic model names and do not identify the CPU.
- Go 1.26.10 (`GOTOOLCHAIN=auto` from `go.mod`), Python 3.13.17 with `paper/requirements.txt`.
- Up to 4 cells ran concurrently (one per vCPU). Decision-cost metrics (wall and CPU time per pass) depend on the
  machine and its load. Every other metric is a deterministic function of the binary, the configuration and the
  seed, with one exception the session never triggered. The upstream baselines run upstream multi-node
  consolidation under a real 1-minute wall-clock timeout
  (`pkg/controllers/disruption/multinodeconsolidation.go`, `MultiNodeConsolidationTimeoutDuration`). A search
  that runs past it returns early, so the decision would depend on machine speed. The pipeline's fine adapter uses
  the injected clock instead. No session or H7 timing run had a pass over 1 minute (`wall_passes_over_1m` is 0 in
  all 1,575 runs; the slowest took 52.3 s, in the one W5 B2 cell). Cells killed by a VM replacement were relaunched
  from scratch, so each run ran on one VM.

## Rebuilding a run

Build the binary at the Gate 3 commit in a separate worktree, and run it from a checkout of the branch head, which
holds the inputs (the Gate 3 tree has no `experiments/runs/session/` and no `h7-timing.yaml`):

```bash
git worktree add /tmp/csim-c78b5f9 c78b5f95063c1995b10fa6d66571a16d0a32b243
(cd /tmp/csim-c78b5f9 && go build -o bin/csim ./hack/consolidation-sim)   # a clean tree, so the VCS stamp is exact
mkdir -p bin && cp /tmp/csim-c78b5f9/bin/csim bin/csim                    # back in the branch-head checkout
bin/csim run --config experiments/runs/session/<run_id>/cell.json --out /tmp/<run_id>
```

The decision log (decompressed), `timeseries.csv`, `podsets.jsonl` and every simulated field of `summary.json`
should come out identical. The evidence is the H7 timing pass, which reran 20 session cells on another VM: every
rerun matched its session twin on all of these (`twin_differences` in `paper/analysis/latency_optimality.py`;
`paper/tables/h7s_runs.md`). The 130 cross-group duplicate sets also have identical summaries. `TestDeterminism`
is narrower. It runs 14 small configurations twice in one process and compares the uncompressed decision-log and
time-series bytes, the integrated cost and the evictions (result at the session commit in
`experiments/session-determinism.txt`). Wall- and CPU-time fields and the manifest's timestamps differ.

## Rebuilding the matrices

```bash
bin/csim matrix --matrix experiments/matrix/session.yaml   --workers 4    # 1,740 cells, seeds 101-110
bin/csim matrix --matrix experiments/matrix/h7-timing.yaml --workers 4 --max-wall 0s   # H7-S: 20 cells, 4 fillers
```

The pilot ran on two earlier binaries, and a later commit (`02ef9ce`, the time-defined steady state and CPU time
per pass) changed simulated outputs, so the Gate 3 binary does not regenerate it. Rebuild each pilot group with its
own binary (built as above, from `c3e9e35` and `2d8fce7`) into a fresh directory:

```bash
bin/csim-c3e9e35 matrix --matrix experiments/matrix/pilot.yaml --only pilot-baselines --out /tmp/pilot --workers 4
bin/csim-2d8fce7 matrix --matrix experiments/matrix/pilot.yaml --only pilot-exp1,pilot-calibrate \
  --out /tmp/pilot --workers 4
```

Run IDs are a hash of each cell's configuration, so a rerun writes the same directory names; the runner skips cells
that already have a `summary.json` and can be re-invoked until it reports `0 pending`. The H7 timing pass runs in one
invocation (no wall budget). Its cells have the configurations of the session's W1 1,000-node
heuristic/entropy-greedy and random/entropy-greedy cells in `exp1-n1000`, so the hash at the end of each run ID
matches, and only their timing fields differ.

The session ran its groups one at a time in the preregistered order, under the driver in
`experiments/session-driver/` (v1, then v3, then v4; v2 was armed but stopped before it acted; the README says
what each changed, and `session.log` is the full log). 1,551 of the 1,740 session cells ran. The four
cut-candidate groups were cut on time alone (`experiments/session-driver/cut-decisions.txt`). `realism-w5` passed
the preregistered start check, but its projection was wrong by more than 30x, and it was stopped under a time-only
overrun rule declared during the session. That rule also cut the three later candidates (deviation 7 in
`experiments/RESULTS.md`). One `realism-w5` cell had finished by then. To run them on a larger machine:

```bash
bin/csim matrix --matrix experiments/matrix/session.yaml --workers $(nproc) \
  --only realism-w5,realism-w6,exp7-b2-n1000,exp1-baselines-n1000
```

`make figures` then includes them, since the completeness rule (10 seeds per configuration) admits them once
they are complete. `exp7-b2-n1000` is a timing comparison (CPU time per pass) against the session's
random/entropy-greedy W1 1,000-node cells, which ran on VM C at 4-way load. Run it in its own invocation beside a
rerun of those cells, interleaved by seed as in `h7-timing.yaml`, or report it as a cross-machine comparison.

## Rebuilding the analysis

```bash
make figures                     # all tables (paper/tables) and figures (paper/figures/out) from experiments/runs
/opt/research-venv/bin/python paper/make_figures.py --only <module>
```

The outputs are byte-reproducible: two runs over the same raw data give identical files. The offline packing bounds
(B6) are cached in `paper/tables/cache/lower_bounds.json`. The cache is not committed, so a fresh clone recomputes
the bounds with CP-SAT on its first run. The solver runs on one worker with a fixed seed and a deterministic work
limit, so the bounds do not depend on the machine's speed. The exception is an instance that hits the 120-second
wall-clock safety limit, which the analysis logs as a warning.

## Parity

```bash
PARITY_STATES=1000  PARITY_SEED=1 go test ./pkg/controllers/disruption/pipeline/ -run TestParity -count=1 -timeout 6h
PARITY_STATES=10000 PARITY_SEED=2 go test ./pkg/controllers/disruption/pipeline/ -run TestParity -count=1 -timeout 30h
```

The 10,000-state run is split into four chunks, one per policy and catalog, each selected with `PARITY_POLICIES`
and `PARITY_CATALOGS` and written to `experiments/parity/chunks/`. The WhenEmptyOrUnderutilized/kwok chunk ran
before the session; the other three run after it under the session driver. For example:

```bash
PARITY_STATES=10000 PARITY_SEED=2 PARITY_POLICIES=Balanced PARITY_CATALOGS=assorted \
  PARITY_OUT=$PWD/experiments/parity/chunks/parity-10000-seed2-balanced-assorted.jsonl \
  go test ./pkg/controllers/disruption/pipeline/ -run TestParity -count=1 -timeout 30h -v
```

Results: `experiments/parity/` and `docs/research/parity.md`.
